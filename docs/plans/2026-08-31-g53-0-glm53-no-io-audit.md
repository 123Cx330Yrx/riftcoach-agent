# G53-0：GLM-5.3 无 I/O 可用性与配置审计

> 本文记录 2026-08-31 在 `8e-productization` 内执行的第一批 G53-0 审计。
> 审计只读取仓库中的非敏感配置、代码和脱敏历史元数据；没有读取任何密钥值，
> 没有创建 Provider 客户端，没有访问网络，也没有调用 Riot、OP.GG 或 GLM。

## 1. 要解决的问题与工程原则

GLM-5.3 不是把 `LLM_MODEL` 从 `glm-5.2` 改成 `glm-5.3` 就能完成的升级。
它的 thinking 语义、账号/端点权限和响应中的 reasoning 字段都可能与当前
Zhipu Adapter 不同。G53-0 的职责是先回答“本地能否证明它可用、应使用什么非敏感
配置”，而不是证明模型质量，更不是提前切换默认模型。

本批遵循两个原则：

1. **先证据，后 I/O**：在账号类型、正式端点、模型 ID 和权限没有可审计证据之前，
   不读取 Key，不发送请求。
2. **保持变量隔离**：GLM-5.2、DeepSeek 旧结果和当前生产运行时保持只读；不把
   未验证的 GLM-5.3 写入默认配置，也不修改 Provider 代码。

## 2. 审计范围与控制流

本批只走以下静态路径：

```text
canonical 状态 / G53 设计与 ADR
        ↓
```

没有进入 `OpenAI(...).chat.completions.create(...)`。现有真实调用脚本
`scripts/probe_zhipu_capabilities.py`、`scripts/test_zhipu_llm.py` 和
`scripts/run_real_provider_skill_slice.py` 均未运行。

## 4. 配置与架构边界

`app/providers/config.py:21-47,105-130` 的 `ZhipuSettings` 只检查 Key、
Base URL、模型字符串非空和超时；它没有账号类型、Plan、region、模型白名单或
thinking profile。`create_zhipu_provider()` 只把 Key、Base URL 和超时交给 SDK。
因此当前系统既不能在离线层证明 GLM-5.3 的权限，也不能安全地把 `glm` provider
别名当成已经注册的 `zhipu` 实例。这个发现属于配置接缝缺口，不是模型质量失败。

当前 `compose.yaml` 的默认值仍然是 `LLM_PROVIDER=zhipu`、
`LLM_DEFAULT_PROVIDER=zhipu`、普通 PaaS 示例端点和 `glm-5.2`。本批没有改动
这些默认值，也没有改动 `.env`。

## 6. 结论、停点与下一闸门

**本地审计结论：`completed-local`；GLM-5.3 采用状态：`blocked/deferred`。**

以下四项仍没有本地可核验的非敏感证据：

1. 账号是 Coding Plan 还是普通 Model API，以及对应权限；
2. 当前账号实际允许的 endpoint/region；
3. 正式可调用的 GLM-5.3 model ID；
4. `thinking=enabled`、`reasoning_effort=low` 在该账号上的实际可用性。

这不是“GLM-5.3 质量失败”，也不是把旧 GLM-5.2 结果判坏；只是按照 ADR-0023
在没有可审计可用性证据时停在 G53-0。若后续获得上述非敏感确认，下一独立批才是
G53-1：抽出显式 thinking profile，做 Fake SDK 离线合同测试；在 G53-1、G53-2
完成前仍不能真实调用或切换默认模型。

## 7. 初学者复述与面试边界

可以这样说：

> 我先做了一个不产生网络请求的 Provider 迁移审计。它确认产品默认仍是 GLM-5.2，
> 现有 Zhipu 接缝固定关闭 thinking，而且本机非敏感配置与 `zhipu` loader 还有
> provider 名称差异；由于没有账号权限和正式 GLM-5.3 模型 ID 的可审计证明，我把
> 结果停在 unknown/deferred，没有读取 Key 或把新模型接入产品。

不能这样说：

> GLM-5.3 已经通过协议或领域准入，或者当前 Coding Plan 端点已经能稳定运行。
