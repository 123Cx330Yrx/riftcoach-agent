# 用宿主真实完成记录绑定独立审查

状态：2026-10-01工程采用；已实现并完成真实工程交接，未启动新付费批或改变产品准入。
这是开发评测取证方案，不改变RiftCoach模型、推理档位、完整上下文标准或产品报告质量要求。

## 为何需要方案层调整

旧方案要求派发正文与最终审查同时可读。当前宿主保留派发路由、作者和turn关联，但加密正文；
审查者实际完成的最终消息可读。四种只读来源均未提供该派发正文，继续补字段不能消除阻断。
官方app-server允许turn/start原生输入，但独立子线程不能由另一个app-server单独resume；
先resume父线程又被当前active writer拒绝。两次诊断均未启动turn、未调用GLM。
不夺取父线程写锁、修改宿主记录或对密文解密，也不反复重派任务碰运气。

官方依据：https://developers.openai.com/codex/app-server
本机generate-json-schema与真实错误回执补充官方未说明的multi-agent写入限制。

## 推荐的具体变化

新执行显式选择证据策略native-final-attestation-v1，不把它伪装成旧v2默认明文证据。
只从安装宿主的只读接口取得冻结独立线程的已完成turn及唯一final；本地提交文件不能替代。
保留原生父子身份、派发作者/接收者/turn/唯一性/顺序检查及原始记录摘要。
final必须包含与实际阶段逐值一致的六字段binding，以及独立审查正文。审查正文还须按现有
门绑定来源、报告、实际请求/响应和阶段摘要，并接受原有全文/纠错检查；主审仍另行判断。
独立审查任务要求审查者亲自读取原件并核验摘要，不接受只复述主审结论。

唯一证据变化：旧策略从派发正文再次校验六字段；新策略由宿主认证的独立final对这些字段
作出确认，并与执行器从原件重建的绑定核对。派发正文可以不可读，但作者、路由和完成关系
不能缺失。不能用final反推“旧派发原文已经得到证明”，两种证据含义必须显式区分。

## 保留和损失

| 要求 | 新策略如何处理 |
|---|---|
| 真实独立主体，不允许主Agent自写两份稿 | 作者、父子关系和final正文从宿主读取；写两个JSON仍不能通过 |
| 计划/案例/阶段/报告/请求/响应不能串用 | final六字段对比执行器重建值，逐项错误拒绝；正文按原门再验 |
| 不接受未完成或失败审查 | 唯一已完成turn和final；429/402、无final、拒绝及矛盾仍阻断 |
| 原生派发来源 | 保留可读路由/作者/接收者/turn及顺序；不再证明派发正文逐字内容 |
| 旧批次和费用 | 只读、不补签、不重开；费用和未知用量保留，未来新批重新核对累计预算 |
| 原15与生产准入 | 工程往返不增加资格；不得把旧失败批的新解释当成产品成功 |

失去的能力是独立重建派发正文，并将它与最终绑定作双向核对。新方案依赖独立审查者在真实
final中准确确认所审原件；正文中的摘要与业务判断仍须验证。它不解决审查者被误导或主子同源
模型的共同偏差，这些属于实际审查质量与正反例验证，旧明文方案也不能仅靠哈希解决。
本地宿主日志和只读接口仍是相同信任边界；不声称对控制整台机器的攻击者提供密码学保护。

## 验证和实施范围

1. 只读检查现有真实完成记录，验证宿主作者、唯一final、六字段及原件摘要可相互核对。
   当前旧v2必须继续拒绝它；结果只标可行性，不写正式审查或资格回执。
2. 独立复核此提案，重点检查同主体伪造、旧事件重放、跨任务/版本/阶段替换和可用性缺口。
3. 在现有v2适配器中显式适配新证据策略，保持旧v2只读规则不变，冻结策略与实际主体。
   覆盖正例、身份错、六字段各错、缺/多final、未完成、路由错、正文变更和封存重放。
4. 新策略先完成真实独立工程审查→导入→主审→封存→回读的零GLM往返；不能只跑替身。
   通过后才准备未完成质量验证的具体新批、累计预算和已有授权适用性，仍首实质失败停。

备选是保持旧合同，等待宿主支持稳定可读的派发正文；目前没有已验证可用入口或恢复时间。
不推荐退回主审自签双稿、把密文当明文、跳过独立审查或降低模型验收标准。

## 采用理由、完成证据与局限

主Agent在既有工程修复授权内采用此策略：保留真实独立主体、实际原件绑定和原有质量门，
纠正对不可读派发正文的工程依赖，不把技术实现条件追加成用户必须裁决的产品要求。
独立方案复核accepted_for_implementation，后续补丁独立复核无阻断；三份核心源码哈希
逐一匹配审查记录。不建立新的草稿版本、签署体系、全局事件消费库或额外产品Agent。
取证意义的损失如上表保留，不能声称哈希证明审查者确实阅读，也不追认历史密文失败事件。

实现复用read_collaboration_dispatch、HostReviewEventSource和validate_independent_event。
host_review_evidence_policy显式进入计划SHA、事件与原始证据摘要；未知策略拒绝，缺省仍旧策略。
首次入口可显式冻结新策略；续批复用同一预检选择，但原固定已停批不可重开。
若派发有可读正文且与final冲突，仍拒绝；密文只允许已确认的路由头加非空密文形态。
