# 5D-7 V2 预算可达性裁决设计

## 1. 具体问题

DeepSeek V4 Pro V2 held-out 的第一个案例已经得到一条可规范化的真实响应，实际
Usage 为 3241 input + 199 output = 3440 tokens。领域单例上限是 4000，单请求
最大输出预留是 1024。第二次 Agent 调用发出前，账本必须验证：

```text
3440 + 1024 <= 4000
```

该条件不成立，因此请求在 Provider I/O 前被阻止。完整案例原本至少还需要一次
工具结果后的 Agent 调用和一次独立 Evaluation。V2 所测出的首先是实验资源合同
不可达，而不是报告质量不合格。

当前缺少一项自动化保障：已有 Fake Provider 使用极小的固定 Usage，能够证明控制流
连接正确，却不能证明真实长度的请求在预算内可达。

## 2. 原理：安全上限与可行预算不是同一件事

- 安全上限回答“最多允许花多少资源”；
- 可行预算回答“完成被测控制流是否至少有机会”；
- 一个 fail-closed 上限即使正确执行，也可能把所有合格候选都挡在必经步骤之前；
- 此时不能放宽原考卷重跑，也不能把失败直接归因给模型。

因此，任何新的真实领域门都必须在调用 Key 前完成预算可达性检查。

## 3. 方案比较

### 方案 A：修改 V2 上限后重跑

拒绝。V2 已经执行并暴露了首题行为，修改资源合同会污染 held-out 身份，也会覆盖
“原门不可达”这一真实历史。

### 方案 B：立即关闭 DeepSeek 领域候选

拒绝。V2 没有完成草稿和 Evaluation，证据不足以判断模型的领域报告能力。

### 方案 C：离线分层裁决后再决定是否设计 V3

采用。先绑定不可变 V2 结果的精确 SHA-256，产生两类不混淆的证据：

1. 基于真实 Usage 和账本预留规则的精确“下一调用不可达”证明；
2. 基于真实生产控制流请求长度的校准投影，用来防止不现实的 Fake Usage 再次通过。

投影只用于风险暴露，不声称是 Provider 官方 tokenizer，也不直接给出 V3 推荐上限。

## 4. 本批实现与排除项

实现：

- 严格、只含安全字段的预算可达性合同；
- V2 结果精确哈希和关键语义复读；
- 下一次调用的精确最低门槛与短缺量；
- 三阶段真实本地请求 envelope：初始 Agent、工具往返后 Agent、Evaluation；
- 用首轮真实 input Usage 校准的长度投影；
- 明确的 V3 决策门：预算仍未校准完成前，不得真实调用。

不实现：

- 不调用 DeepSeek、GLM 或任何外部 Provider；
- 不读取 `.env` 或 API Key；
- 不修改 V2 文件、Prompt、Context、Skill、Harness 或 Provider 默认值；
- 不创建 V3 Dataset、结果路径或真实运行入口；
- 不引入 LangGraph、SDK、Multi-Agent、前端或新依赖。

## 5. 数据流与控制流

```text
V2 不可变结果 bytes
  -> SHA-256 与严格 Pydantic 复读
  -> 提取首例真实 Usage / 单例上限 / stop code
  -> 计算 3440 + 1024 = 4464
  -> 判定当前 4000 无法发出下一请求

V2 冻结输入 + 现有生产执行器 + 本地脚本 Provider
  -> 捕获 3 个 ChatRequest（不保存正文）
  -> 计算 message 数、角色和 tokenizer-free 长度单位
  -> 以首轮真实 3241 input 校准长度比例
  -> 形成“投影，不是官方 Token”证据

两路证据
  -> V2 维持 admitted=false
  -> 模型质量保持 unknown
  -> V3 只有在新资源合同和新身份完成后才可被考虑
```

## 6. 非功能要求与失败模式

- **安全**：输出合同禁止 prompt、response、API Key、request ID 和异常正文；
- **可追溯**：绑定 V2 文件 SHA、experiment ID、case ID 和模型身份；
- **确定性**：离线 envelope 测量使用稳定 ContextSizer，测试结果可复现；
- **诚实性**：精确结论与校准投影使用不同字段和状态；
- **失败关闭**：结果 SHA、案例状态、Usage、stop code 或三阶段顺序漂移时拒绝裁决；
- **无外部副作用**：模块不接受 Provider、凭据或网络客户端。

## 7. 测试如何证明行为

测试必须证明：

1. 精确 V2 结果可复读且当前门在第二次调用前必然失败；
2. 错误 SHA 或漂移语义被拒绝；
3. 真实生产控制流本地形成初始 Agent、工具后 Agent、Evaluation 三类请求；
4. 长度校准投影不会被标记成精确 Provider Usage；
5. 系统拒绝凭现有证据生成一个“推荐 V3 Token 上限”；
6. 序列化结果不包含敏感正文或扩展字段。

## 8. 局限与后续

现有公开 V2 记录刻意不保留原始 ToolCall 和第二轮请求，因此无法恢复 V2 当时完整
链路的精确 Provider Token；本批也不会尝试恢复临时输出。下一批若继续 V3，必须先用
新的开发集或不含 held-out 答案的校准流程确定资源合同，再创建新的 Dataset/Context/
结果身份。V2 永久保持不可变的 `admitted=false`。
