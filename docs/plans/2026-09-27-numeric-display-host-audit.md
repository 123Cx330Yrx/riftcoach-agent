## 裁决

**我不认为现有证据足以把本次 `8.80` 定性为原采用标准下已证实、必须阻断的 `wrong_correction`。更准确的发现是：源报告值与重新计算值采用不同展示结果，而当前自然语言合同没有明确规定“每个输出数字的尾随零都构成重新计算精度的承诺”。此前拒绝理由把一个可辩护的严格解释写成了唯一明确规则。**

这不是说 `8.805` 按两位 HALF_UP 可以得到 `8.80`。该运算确实得到 `8.81`。如果本次文本明确声称“从原始值重算并保留两位小数，结果为 8.80”，它应拒绝。现在的文本没有这项精度声明；它引用了实际提供的确定性来源 `8.8`，同段又明确写出 computed `8.81`，并在解释与修法中保留原精度 `8.805`。把 `8.8` 写为数值相等的 `8.80`，不等同于已经证明模型重新做了错误的两位舍入。

按已采用的完整上下文标准，这更接近可以统一/说明展示精度的表达问题；其唯一问题定位、比较范围、差距方向、样本构成解释和修法均有来源支持。不能只因没有额外写“沿用一位来源展示”就新增词义定义门槛。也不能把这一判断扩大成“任何微小数值错都可以忽略”：本例的依据是**确有被引用的数值相等来源、正确原精度值和正确 computed 值共同存在**，不是新设通用容差。

仍保留两个限制：

1. “所有自然语言统计数字按书写小数位重新计算”在旧工作流中确有先例，因此原拒绝并非毫无出处；但需证明该更具体规则作为当前解释/修法的通用约束仍被明确采用，不能从 computed 字段的两位属性直接推出。
2. 本审计不把已经闭批的运行自动改为通过，不补造编辑/终评、及时双审或完整原15资格。历史记录与本次标准争议应并列保存。

## 当前请求实际规定了什么

实际 `messages[0].content` 包含：

> 数字先原精度计算再HALF_UP

同时规定：

> 完整上下文已足以确定含义且符合来源时，仅改善措辞、强调限定或避免脱离上下文误读的建议不作为错误。

以及：

> 审查输出也必须遵守上述事实、范围与来源规则。

实际 system 中 `原句小数位`、`两位`、`小数位` 均为零次；工具 schema 也没有为自然语言数字声明 `places`、有效位数或统一两位输出规则。它要求按正确的算术方式计算，**没有完整定义每个文本数字如何选择量化位数，也没有明确禁止对 source-reported 值补尾零**。

实际 `messages[1]` 中的：

```text
computed_evidence.numeric_format.win_loss_places = 2
computed_evidence.numeric_format.win_loss_rounding = ROUND_HALF_UP
```

明确描述的是 computed 表中 `win_mean/loss_mean` 的编码精度。这可用于解释该表为什么写 `8.81`，不能单独扩张为“报告/解释/修法中的每个数字都必须以自身最后一位为重新运算目标精度”。同份输入允许原报告保留 `8.805`、`33.5`、`34.0` 等不同精度，因此“所有数一律两位”显然不是合同。

ADR0102 的 `2026-09-15 Owner-approved whole-context standard and single decision protocol`（约1300行）记录用户采用完整上下文标准，明确可选措辞改善不能单独阻断，但真正事实错误和矛盾仍阻断。其 `Context-sensitive rubric and old labels`（约2237行）也要求区分事实错、无依据推断、未解范围与可选编辑改善，不把合同不匹配本身泛化成语义失败。

ADR0112 保持完整上下文标准；ADR0113 要求审查输出与修法逐项有来源支持，并禁止严格原15走“附属错误例外”。**禁止错误例外并不免除先证明这里确实有错误的责任。**

## 本次原文与来源的对应关系

source 22 是完整确定性来源。其赢输局表和后文统计描述均为：胜均值 `8.8`，败均值 `6.45`，差值 `2.35`（按展示均值计算）。实际事实表的 aggregate 同样记录 `8.8`；其 provenance 明示 `operation=source_reported`、`recomputed=false`。

source 31 是 computed 数据。所选与 MIDDLE 两组的获胜成员都是表行 `[2,6]`，分别为 `8.95` 和 `8.66`，computed 两位值均为 `8.81`。实际 role 统计与原报告都给出 `8.805`。

只读 Decimal 复核：

```text
(8.95 + 8.66) / 2 = 8.805
HALF_UP 到一位 = 8.8
HALF_UP 到两位 = 8.81
Decimal('8.8') == Decimal('8.80') = True
(1.34 + 9.64 + 8.38) / 3 = 6.453333333333...
原精度胜负差 = 2.351666666666...，两位 HALF_UP = 2.35
中单败均值 = (9.64 + 8.38) / 2 = 9.01
```

真实 explanation 写的是：

> 实际数值为：胜局（薇古丝 8.95、辛德拉 8.66）均值 8.80……来源的赢输局对比表与 computed_evidence（selected cohort：win_mean 8.81、loss_mean 6.45）均给出该差距。

它没有逐字写“由这两行重新计算并四舍五入到两位得到8.80”。列成员后说均值，在脱离来源时很容易读成新计算结果，这是严格拒绝解释的最强依据；**但完整同段同时点名来源表和 computed 的不同显示值，后句还保留 `8.805`**，所以不能忽略上下文而把前述加强版计算声明当作模型原话。

suggested_correction 同样先写中单胜均值 `8.805`，后写混合胜局 `8.80`。两组获胜成员相同，精确量不因混入辅助败局而变化。该写法的精度不统一，统一为 `8.805` 或 `8.81` 会更清楚；现有来源足以解释它为同一均值的不同显示，而没有错误地改变获胜成员、分母或 CS 结论。

原报告 block 6 的真错是把“中单补刀基本持平”扩大为“混合全部五局也持平”。输出准确指出并修复它；`2.35` 是从原精度计算也正确的两位差值，并不依赖错误地用 `8.81 - 6.45 = 2.36`。辅助单局 `1.34` 拉低混合败均值的样本构成解释成立。没有新增经济或伤害归因。

## 反对本裁决的证据及其限度

不能声称过去完全没有“按文本小数位”规则。旧 `app/evaluation/golden_evidence_requests_v8.py:29` 明确写过：

> 报告展示统一按十进制ROUND_HALF_UP舍入到原句小数位（8.805保留两位为8.81）

`golden_fact_requests.py`、typed numeric validators 也有按原 token 位数校验的历史实现。ADR0102 历史段要求完整数值检查继续执行，并记载全精度后 HALF_UP。若任务是执行这些旧 typed 合同中显式 `reported/places` 绑定的比较，`8.80` 应失败；正确样本结论不能豁免明示数字约束。

但本次属于1.5.4 coarse native opinion合同：实际输出只有自然语言 explanation/correction，没有旧 typed 运算/精度绑定；`RoleCorrectionScopeReviewWorkflow -> RoleCoarseReviewWorkflow.validate_sources` 也没有重新执行旧逐 token 算子。后一点不证明语义正确，只说明不能拿另一个合同的具体格式推导，冒充本次已经明确给模型和验收者的通用规则。

所以这里存在**精度解释未闭合**，不是数学上 `HALF_UP` 本身矛盾：同一输入保留 source-reported `8.8` 和 derived `8.81`，但没有完整界定“忠实复述来源展示”“重算派生值”和“补尾零”之间的选择规则。此前审查直接以尾零推断新做两位舍入，再以缺少逐数字声明拒绝，存在人为抬高门槛的风险。

## 不能证明的点与最小处理

- 不能由输出证明模型内部究竟复制源值、使用 half-even、做了错误计算还是只补了零；本审计不猜内部原因。
- 不能由 `8.80 == 8.8` 推出精确均值就是8.80，也不能容忍明确声称“两位HALF_UP为8.80”的文本。
- 不能把当前争议自动改成原15通过；运行已停止，没有本例实际编辑/fresh终评，其后未启动案例也没有任何新增证据。
- 不能声称 source 22 的生产链原本有合法的一位舍入政策。请求可见结果是一位显示，但原生产精度如何丢失需另核原代码；这不应由尾零反推。

最小处理是保留本次所有原件和已有 host 决定，在新的审计说明中记录“停止发生，但数值错误的阻断定性有标准争议”。不要先改提示、补数字协议或发新批。先把现有生产者的 source-reported 与 recomputed 精度语义查清，并明确后续究竟要求什么：普通忠实展示可保留原显示/补零，还是所有新统计陈述必须从原值按明确输出精度重新运算。后者是可采用的严格规则，但不能只靠 computed 字段元数据和历史别的合同来隐式施加。

就本例内容本身，采用完整上下文的审计意见是：定位与修法方向成立，`8.80` 可由已引来源解释，精度统一属于可读性改进；目前不足以维持“已证实错误修法”这一强定性。这个独立意见与之前拒绝记录并列，供主任务裁决，不回写历史。
