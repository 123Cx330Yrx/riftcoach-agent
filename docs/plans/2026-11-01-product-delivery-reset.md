# RiftCoach 产品推进与验收计划

**Goal:** 先交付普通用户可发起、可恢复、可核源、可阅读的可信复盘，再按既有路线完成 Coach / Review / Training / Evidence 联动和整体体验。
**Architecture:** 复用现有 API → SQL 任务 → Worker → 来源/Memory → Flash 生成 → Sol 双审 → 必要时唯一修订与同稿双 fresh → Evidence/报告查询路径。传输、任务执行、内容质量、界面消费分别验证；开发诊断不进入产品正常使用流程。
**Tech Stack:** 现有 Python Runtime、PostgreSQL、Responses及显式Chat接收器、React/TypeScript、pytest 与 Playwright；本计划不引入框架或新 Agent 栈。
**Status:** P1_complete / P2_partial_verified / P3_not_accepted。2026-11-03同任务受控续接已完成双初审、唯一确定性应用、同稿双fresh及SQL/API/1440与320浏览器消费；累计7HTTP/100656known，unknown/retry/未决均0。四次审查许可已全部消费，进程/容器和monitor已收尾。原三次生成32768请求配置违规保留；正常生成请求16384/300上限已离线修复（151项定向/SQL检查、12Runtime/2清单通过，当前提交CI待核），随后按依赖处理来源范围表述与P4玩家阅读。国服称呼/外号和自然教练口吻是既有必做要求，本轮提醒不改变优先级。详细真实结果见sol_product_chat_review_continuation_completed_20261103.json及[Chat工作卡](2026-11-01-chat-candidate-offline.md)。代表性闭环已实证，不等于P3全部验收或日常使用准入；原15、Stage8E/默认准入不变。

## 2. 每项工作的固定逻辑

按“用户结果 → 阻断证据 → 修正机制 → 最便宜的区分性验证 → 实际消费验收 → 收口”推进。

每个工作包只在现有记录中回答六个问题，不为每条命令新开审批/工作卡：

1. 用户现在做不成什么？对应哪一个交付结果？
2. 哪些是实际证据，哪些是解释，缺什么信息才能区分？
3. 哪个现有模块应负责，哪些行为必须保持？
4. 最小修改如何作用于故障，什么证据会否定这个方案？
5. 测试具体观察什么、通过后能说明什么、还不能说明什么？
6. 成功如何收口，失败属于局部缺陷、路线反证还是预算/授权边界？

只有能消除当前业务缺口或回答路线选择的问题才进入当前队列。维护、诊断和归档本身不计产品功能完成。进度汇报固定包含“解锁的用户能力 / 新证据 / 剩余阻断 / 实际成本 / 下一项结果”，测试数量只作附件。

## 3. 推进顺序与每包完成条件

### P1：审查通道的采用裁决与离线缺口清单

这是恢复执行后唯一首项交付；先形成裁决，不直接启动 attempt-14，也不预设继续修未知事件。

**要回答：** 当前通道是否有清楚、可验证的协议边界，能承担长输入、工具返回和多次审查？现有协议拒绝究竟来自本地接收器、SDK 转换还是中转契约？无法区分的部分必须明确留空。

**做法：**

- 使用现有 5 次 524、完整流式诊断和 3 次产品协议失败材料，画一条数据路径：HTTP/SSE → SDK → 接收器 → 业务校验 → 任务状态 → 发布。
- 列出接收不变量：请求/响应身份、事件顺序、工具调用身份与参数、完整终态、usage、关闭/取消。将业务正确性要求与通道专有格式规则分开；不因形式更严格就认为业务更安全，也不因 completed 就放行。
- 优先查已有实现和明确的提供方协议说明。未知事件只有哈希不能还原其含义；不得把合成 ping、历史不同请求或猜测当现场证据。
- 若需要后续改善观测，先定义并验证安全元数据：协议事件标识的受限表示、顺序、字段缺失/null/类型/冲突的区别、首个拒绝及有界上下文。凭据、正文和私有 reasoning 不进入诊断输出；如安全边界下仍无法识别，结论就是证据不足，不能默默忽略。
- 同时用现有报告核查两个已知语义问题第一次出现在哪层：来源聚合/舍入，及 observed 用户约束到生成与修订的传递。只定位，不预设“再改提示词”或把最终数字硬编码。

**比较选项，按证据选择一条：**

| 选项 | 采用条件 | 否决/退出条件 |
|---|---|---|
| 保留当前模型与通道，修正接收器 | 有明确协议依据或可复现的真实安全材料，兼容规则可列举且不损害业务不变量 | 只能逐次猜未知事件、每次付费发现新形态、无法验证内容边界 |
| 保留业务角色，使用已核实的其他兼容通道 | 实际可用、契约明确、完整工作量可承受，成本/来源/参数差异已比较；另按实际授权范围决定 | 仅凭名称/宣传认定可靠，或偷偷改变模型/推理档位/数据去向 |
| 暂不进行真实审查接线 | 没有路线满足上述条件时给出明确缺口及可行选择；继续独立离线产品事项 | 不允许以无限兼容和更多一次性恢复来维持“正在接近完成”的叙事 |

第一选项只是优先评估对象，不是既定结论。回到相同非流式请求不是默认备选，已有 5 次约 130 秒的 524 是反证。

**交付：** 一份简短裁决：选项、证据、不可证明部分、受影响模块、是否确需真实探测、完整闭环资源估算。若缺失信息必须在线取得，先做可审查的取证方案；不得用昂贵产品全链替代未定义的取证任务。此包完成不等于通道真实通过。

### P2：修好产品边界，形成可重现的离线闭环

依赖 P1 明确的责任边界；没有通道选择时，只推进不依赖该选择的数值、身份、任务和 UI 缺口，不更换主目标或开新实验路线。

**只修已证问题及同机制受影响调用者：**

- 接收器：按选定契约处理流，已知合法事件通过，身份切换、参数冲突、截断、缺终态等正确停止；实际成功和失败都可解释。
- 内容：数值按真实来源精度及约定舍入复算；明确他人观摩和本人训练的对象/用途，缺失本人数据不伪造个人基线。检查 generation → review → repair 的约束传递，不只拦两个固定短语。
- 状态：外部超时、协议无效、本地文件/锁故障、语义需要修订、取消分别得到合适的任务状态。一次本地可恢复异常不能逼迫重新生成或制作另一套一次性恢复脚本。
- 恢复：优先用现有普通 resume、幂等和 checkpoint。只补经测试证明的通用缺口，不先大重构；旧特殊恢复保持历史用途，不自动扩为无限历史兼容。
- 发布：双审对同稿；确需修订时唯一 application、双 fresh 同实际新稿；未解决真实错误不能发布。可选措辞和正常舍入不升级为阻断。

**离线完成条件：** 第 4 节中受影响的正/反/恢复案例通过；一条接近真实的 SDK → Worker → SQL → API → 浏览器路径使用替身提供方跑通。旧已通过且输入未变的检查复用，只补缺失覆盖。模型替身只能证明编排行为，不计新增模型质量证据。

### P3：准备一次能回答交付问题的真实验收

不得用“还剩一次授权”决定实验目标。先明确要验证通道，还是要交付整条产品链。

- 若 P1 仍需通道实证，取证须预先固定假设、观测、请求规模、结果对应的去留；可以用一次代表性产品请求同时取得通道和业务证据，但只有全部校验通过才计为正式结果。hello 不能证明长工作量可靠；另做诊断请求时单独列账，不导入其意见。
- 在真实执行前，为全部必需后续留足调用数、tokens 和活动时间。原任务实际有 3 次生成，若需双初审与双 fresh，成功路径就是至少 7 次，而不是把最短 6 次当普遍保证。额外检索和重试共享弹性额度。
- 用真实构造的输入与输出包络、已有用时估算可达性；每步还需重新核剩余预算，尤其修订前要覆盖两项 fresh。估算可行不是保证；不够时保留进度并说明，不先购买注定无法完成的下一步。
- 原任务已无足够额度且无新付费授权。未来续旧任务或开展独立新案例必须有具体、合法的范围/预算决定；不得延长旧授权、回退 DB、另起账本抹去成本，或把本计划当授权。
- 同一实现完成相称本地检查后合并一个可审查提交，固定干净 HEAD，满足现有同 HEAD CI 要求。不要每写一段计划触发新 CI；已终局 CI 不重复查询，查询失败不等于测试失败。

**交付：** 实际入口、输入/来源、完整成功与失败路径、资源上限、已有证据、未验证问题和停止条件组成一个可审查验收包。只有需要新的费用/外部范围决定时再问；已授权的离线准备自主完成。

### P4：真实产品闭环与页面验收

从普通产品入口发起/恢复 → 实际 Worker/SQL → 真实模型 → 发布查询和浏览器阅读；外置工具只负责受控执行与取证，不替用户逐段改业务状态。

- 逐份实读来源、请求、审查、修订和最终报告；独立复算数值，检查身份/用途/版本/来源覆盖。模型 pass/高分、HTTP200、Worker succeeded 均不能单独判成功。
- 检查正常直接通过与需要修订的分支：实际走到的分支才有真实运行证据，其余不能写成已实测。开发独立验收用于核质量，不成为每份线上报告的人工依赖。
- 浏览器检查普通用户能发起、理解进度/错误、查看报告并回跳证据；刷新/重启后状态和费用一致，双击/刷新不重复发起。桌面、手机、键盘、加载/空/错态均有对应检查。
- 失败时按第 5 节归因；不在现场连续改接收规则并自动再买下一次。结束时核费用、未决请求、进程和临时资源。

**完成条件：** 一个完整真实闭环、内容人工验收通过、实际报告和 Evidence 可读、账目与状态一致。若依赖特殊迁移或超出默认预算，只记“受控恢复成功”，不能算正常产品合同通过。

### P5：受控日常使用质量与既有产品后续

代表性成功后先检查证据差距，再决定新增验证，不能立即把熟悉稿成功推广成普遍可靠。

- 冻结实现/政策后，用未参与针对性修复的新任务验证迁移性。首轮建议两份新观摩任务：一份有足量来源但位置/输赢构成不同，另一份样本少或存在明确的非关键来源缺失，检查是否诚实限制结论。两份都保留 observed 用途边界，在看模型结果前固定输入、全文核源标准与应允许/拒绝的结论。关键来源不足应正确暂停而非强求报告；正确处理也计入产品行为观察，不能算成功报告。
- 这是两份任务的有界方案，不是两次模型请求，也不是完整可靠率评估。实际总调用、tokens、时间须按 P3 对每份完整路径测算并单列；本计划不授权它们。若 P1 选择改变业务模型/政策而非仅传输，先重新核受影响语义覆盖，不能仍声称两份足够；不得自动扩批或机械重跑 15。
- 旧已知错误作为开发回归；新任务作为独立观察，二者分开。修订使用的新问题同时回看正确内容是否被破坏，不能只验原错误消失。
- 公布实际完成/失败数及分母、成本、首字节/总时延和原因。少量案例不宣称 99% 稳定性；若希望承诺稳定率，另按目标和观察量设计评估，不凭空加阈值。
- 支持受控采用后，恢复下表的产品交付；完成 8E 仍按既有路线和退出条件，不能因本计划自设新主阶段。

| 后续产品结果 | 依赖与验收方式 |
|---|---|
| Review 与 Evidence 可理解 | 近期/单局/Timeline 的对象、结论和来源一致；可从结论定位依据，不堆日志代替解释 |

## 4. 测什么、改什么、验证什么

| 层次 | 必测行为/证据 | 失败应改哪里 | 通过说明与局限 |
|---|---|---|---|
| 来源与数值 | 来源→聚合→展示精度；完整报告复算；正确舍入与真错误成对，检查样本/位置/版本 | 第一个产生偏差的转换层；仅当约束传递错才改输入 | 证明数据与确定性规则；不证明模型整体理解 |
| 身份与内容用途 | observed/self 正反例；观摩建议合法，未经依据的个人训练/长期因果断言拒绝；缺数据如实表达 | 请求上下文、生成/审查政策或结果应用的实际缺口 | 已知反例不再漏放且正例不误杀；熟悉例不算新泛化证据 |
| 传输契约 | 实际 SDK 接收边界；合法流、完整工具返回、身份冲突、参数不一致、截断、超时/取消、usage 保留 | 适配器或供应通道；不为绿灯放宽业务完整性 | 本地契约实现正确；合成流不证明实际提供方契约 |
| 任务与账目 | 锁/文件故障、重启、重复 resume/旧 checkpoint、取消竞争、已发送无回执、预算不足；所有已知/未知计费保留 | Worker/Session/SQL 状态投影，或明确的发送边界 | 每请求有确定归属，重复操作不重买成功步骤；不要求重跑已覆盖项目 |
| 审查与修订 | 正确稿直接通过、有效联合补丁、重叠冲突、任一 fresh 真错误、双 fresh 稿件不同 | 现有 workflow/补丁应用/发布校验 | 唯一应用且无已知阻断才可发布；替身通过不证明真实模型检出率 |
| 用户消费 | API/SQL/浏览器同一任务与报告，刷新重启，失败不可读草稿、成功可读，证据跳转，权限和幂等 | 最靠近错误表现且负责该不变量的产品层 | 功能体验可用；无溢出不等于视觉设计好 |
| 真实质量 | 全文核源、已知风险、正确内容保持、新任务与真实耗时费用 | 依据实证定位输入/机制/通道，拒绝先堆提示 | 对验收任务有证据；不以模型自评分或 CI 代替语义结论 |

测试顺序：现有证据复用 → 受影响局部测试 → 有缺口的真实 SQL/Worker/浏览器替身集成 → 同 HEAD CI → 确需的真实提供方/产品验收。后一层不代替前一层，也不重复前一层已回答的问题。新增测试要能在修复前暴露行为缺陷，不能只匹配新源码字符串或重复实现。

缺陷优先级按影响排：先处理错对象/越权/重复付费/账目丢失/错误发布，再处理阻断正常完成和恢复的故障，再处理内容完整性与证据可读性，最后是非阻断措辞和视觉细节。涉及本次交付的实质内容错误必须在发布前解决；视觉整体升级在自己的产品包验收，不以“最后处理”长期搁置。

## 5. 失败后的固定分流

| 新证据 | 后续动作 |
|---|---|
| 已明确的本地软件缺陷 | 保留原失败，用局部可复现反例修具体机制；相称验证后继续已授权范围，不举行新一轮大复盘 |
| 524/上游不可达 | 保留 unknown 与成功前缀；同条件重发没有新信息时不重试，先核外部改变或采用替代路线的依据 |
| 协议拒绝且元数据不足 | 暂停受影响发送，完成契约/观测裁决；不得猜事件意义、删除错误、导入诊断意见 |
| 语义真实错误且存在可靠修法 | 用原意见联合修订并验全文，保留职责漏检；不因为一个 reviewer 漏检就作废全部成功步骤 |
| 不可靠修法、身份/来源冲突、任一最终检查不通过 | 不发布，只停受影响步骤；说明还缺什么证据，不能改分数或标签获得 pass |
| 剩余资源不足完整必需后续 | 在新发送前暂停并给出真实资源/范围选择；不默增、不另起账清零 |
| 修复后只是报错换位置、没有排除新解释 | 当前路线回到 P1 裁决；禁止按“再修一个字段就好”的理由连续付费 |

每次付费失败先分析已有材料；单次补测授权不扩成循环。明确支持继续的证据和实际授权都具备时才续接；不把这条规则变成每个正常成功步骤都向用户重复要许可。

## 6. 达到什么质量才算完成

- **正确：** 验收材料中所有已确认的实质数值/来源/对象/用途错误解决；原正确内容保持，建议能追到依据，缺失和不确定性如实表述。没有已知发布阻断；不宣称零未知错误。
- **可靠：** 声明支持的故障能正确暂停/恢复/取消；同一次操作不重复付费、成功前缀不重做、失败不丢账、不同任务/用户不串数据。不能把经常需要专用脚本救场的链称为日常可用。
- **完整：** 该任务实际要求的双审、应用、同稿双 fresh 和发布消费均有证据；直接通过分支按既有合同执行，不强制无意义修稿。
- **可用：** 普通用户不接触 Control/DB/checkpoint；能理解进度和下一动作，读报告、查证据，刷新后不失状态。
- **可承担：** 成本和时延实测落在采用的产品合同内；特殊追加任务不能替代默认预算验证。若正常路径持续不可达，提出合同/方案取舍，而非继续拿恢复额度掩盖。
- **可维护：** 工作在现有组件与稳定入口内，已解决事项收口，不无限增加 attempt 专用设施；临时物清理，原件保留，重复历史记录用链接而非复制成新队列。
