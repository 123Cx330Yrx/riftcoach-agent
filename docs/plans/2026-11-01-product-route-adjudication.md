## 裁决

当前中转 Responses 通道暂不进入下一轮真实产品验收。选择计划的第三项：停止相同条件的真实补测，完成独立本地修正；尚无已核实的替代通道可直接切换。这个结论只针对现有通道与工作量，不代表 Sol 或所有中转都不可用。

证据见 `data/evaluation/results/sol_product_route_adjudication_20261101.json`：

- 同一首审非流式请求连续 5 次约 129—130 秒 HTTP524；简单退回相同非流式不是有支持的选择。
- 3 次同一流式 wire 请求均完整 HTTP200，但接收契约不满足。call-010 有匿名 created/queued 前导；call-011 首个拒绝为未知事件且无 sequence/response，随后才有有效 created，末尾又出现同类型。两种形态不能互相代替证明。
- 当前路径是 HTTP/SSE → SDK 解析 → `model_dump` → 接收器 → 业务校验 → Worker/发布。已有事件观测在 SDK 之后，没有原始类型文本/额外字段内容，因此不能归因到中转、SDK 或具体扩展，更不能确认是 ping。
- 查阅提供方公开文档主页 `https://doc.yujianwudi.top/`，该页介绍通用接入和 Chat Completions，没有 Responses 流事件契约。它不证明不存在其他协议说明，但不足以支持兼容规则。官方 `https://developers.openai.com/api/reference/resources/responses/streaming-events` 页面抽取的 59 个 response 事件名也无一个匹配现场未知类型摘要；官方文档不自动成为中转的履约证明。
- 同一流式 wire 的报告用量有 21472、46503、22409 tokens。保留真实回执值；差异本身不能证明模型身份、缓存、路由或计费原因。

保留的接收不变量：响应身份不切换，顺序可解释，工具调用和参数完整且一致，终态和 usage 可归属，进程关闭/取消确定。不能为了通过忽略未知事件、删除错误，也不能把 completed 当成业务通过。旧意见仍是被拒绝的诊断材料。

## 内容缺陷及修改边界

### 均值舍入

8.13/1280.91 首先出现在确定性 `player_summary.recent_summary`，报告复制了它；不能把责任归结为模型算错。赢局展示值 8.71、7.56 的均值为 8.135，936.73、1625.10 的均值为 1280.915；按现有 HALF_UP 应为 8.14、1280.92。用底层 CS/伤害与时长再算，这两个例子的相应舍入结果相同。

修正 `app/lol/match_analyzer.py::aggregate_recent_matches`，将参与平均的已发布逐局值转 Decimal，比例先按 Decimal 平均再缩放，最后执行 HALF_UP。不改变分组、权重、逐局精度、空组/缺失行为，不重写旧 Summary、稿件或原始失败。9 个新增行为测试在原实现中 4 失败/5 通过；修正后与来源缺失、阶段1管道、应用组装共 65 项通过。

### 观摩用途

真实生成和审查请求均已包含“观摩对象不是阅读者本人、练习限于观摩”的约束，故不是简单漏传。问题是：服务器约束被放进 data-only 用户字段，而可信通用目标策略鼓励未指定目标时给个人训练选项；固定“训练计划”标题也可能强化这种歧义。这证明存在指令层级冲突，不证明模型内部究竟如何决策。

产品合同升级至 1.7.2：从服务器冻结的任务关系取得 observed/self/unbound，用于必选可信生成区块及双方初审/修订/复审请求。观摩只给观摩练习；本人任务保留明确多位置目标或未知目标时的条件选项；无关系绑定不假定为本人。用户字段、名称、知识和 Memory 正文不能更改用途。复用现有完整来源、补丁应用和双 fresh 机制，独立保存 product review context；旧 qualification 政策和冻结请求不改。

合同摘要和原任务绑定不同，旧终态不能在新合同下自动继续；未来若考虑恢复须单独证明兼容与预算，不借本次修正重发生成。离线测试只能证明用途传递、请求绑定和修订编排，不能证明模型能始终遵循语义规则。
