# 自然任务互补审查：调用路径与预算取舍

2026-10-14；审计基线 `596fd96b4418cb2b3d0a8b052faac599c2c340f9`。
当前结论为零付费工程审计，不是新的模型试验、产品合同变更或准入。

## 结论与待决定事项

固定报告链成功没有消除自然 Agent 的检索轮次。准确表述是：**一次模型选工具、读取结果成稿，
再双初审，直接通过共4次；若需要程序补丁和双fresh，最少6次。** 追加一轮工具选择则分别为5/7次。
因此旧“自然任务固定6次”应缩小为“单轮工具检索且进入修订的最短路径6次”。

推荐保留动态检索和互补审查，准备**显式6次候选**，但此处没有采用或实施。
待用户决定的唯一合同差异是 `max_calls: 5 -> 6`；保留401920总tokens、900秒整任务、
64000单次输入、32768输出、当前产品300秒单请求上限和零SDK重试。
600秒是固定报告开发传输的独立身份，不能借本决定移植。生成仍Flash/high，审查仍GLM/high，
程序原样应用补丁；没有新增Flash编辑请求。模型分工的新修订方式仍须独立身份与资格验证。

这个选择只让最短修订路径有可能完成，不承诺任意自然任务都能在6次或900秒内完成。
它不授权新付费批、不复用旧授权、不变更默认产品、不把开发Host作为生产步骤。
若用户保持5次，则保留原合同；本分离职责候选的普通修订路径不进入生产，不通过删职责或跳fresh腾位置。

## 实际代码路径

| 环节 | 当前实现及含义 |
|---|---|
| 输入与事实 | `app/product/recent_review_service.py::_review_from_summary` 在Runtime前建立确定性报告及可选Evidence投影；Riot摘要获取不计为LLM调用，但不是零外部I/O。 |
| 请求编译 | `app/product/recent_review.py::compile` 绑定summary、report、focus、Memory关系和身份；typed recent入口不代表所有自然Coach/Training路由已完成。 |
| 唯一共享账本 | `app/runtime/runtime.py::RuntimeExecutionFactory.build` 把同一个 `CoachBudgetedProvider` 交给Agent和审查Workflow；不能另开审查预算。 |
| 模型选择工具 | `app/agent/loop.py` 第一次 `provider.chat` 返回真实工具调用；同一响应可有多个knowledge.search，不按工具数量虚增模型调用。 |
| 执行与读取 | ToolRuntime执行知识查询，工具消息进入下一次 `provider.chat`，模型才能依据结果成稿。若再次选择工具，则还需要后续模型调用。 |
| 证据绑定 | `app/agent/draft.py` 仅从实际工具执行建立KnowledgeEvidence；`runtime.py` 配置至少1来源，`app/harness/runtime.py` 缺来源时拒绝。 |
| 检索恢复 | `app/rag/coaching_query.py` 对已知词和无结果作本地查询扩展，无额外LLM，不能把它误算成第二次生成；它也不替代模型按用户任务选工具。 |
| 开发补丁链 | `scripts/review_duty_patch_execution.py` 四个模型slot，另有六个Host验收；compatibility/edit不收费但是真实人工语义工作。不是已接入产品的Workflow。 |
| 生产身份 | `app/runtime/reviewer_roles.py` 对phase、projection和schema作精确选择；当前产品注册不能直接接收开发补丁身份。不得用旧identity伪装新行为。 |

这里的“两次生成”不是重复写两遍报告，也不是一次HTTP分块被重复计费。
已有真实应用记录（ADR0109的2026-09-23节）同样是两次Flash、三次本地知识查询，再一次GLM初评；
当时GLM通过却经独立审查发现日期错误，历史失败保持。本轮不拿该记录授予当前候选质量。

## 可行选择与代价

| 选择 | 调用账本 | 优点与限制 | 裁决 |
|---|---|---|---|
| 动态检索+互补初审/fresh+程序补丁 | 最短4/6，更多工具轮次更多调用 | 保留本次有单例支持的职责划分与Agent选工具；需显式改变5次上限，仍可能超时/拒绝 | 推荐6次候选，待用户决定 |
| 保持5次，双初审过就发布；需修订就停 | 一轮检索直接通过4，修订不能完成 | 合同不扩容，但普通可修错误没有完整修订路径 | 可保留失败关闭行为，不宣称候选已解决自然修订 |
| 确定性预检索+一次成稿 | 理论3/5 | 既有SequentialDraftPreparer/LocalRagAdapter可复用；改变检索选择机制，固定主题可能遗漏focus/Memory/任务所需证据；当前Agent证据接线也须迁移 | 不是等价省调用，不为追求5次而自动采用 |
| 两职责在一次请求内共同审查，初审一次/fresh一次 | 一轮工具为3/4 | 不删职责也可减少请求；但取消独立请求的任务隔离，回到多任务负担，现有单例不足以支持其可靠性 | 合法待评备选，不拼两种协议的成功或现在另开付费比较 |
| 并发双审 | 调用数仍4/6 | 可能减少墙钟，但不减少HTTP/tokens；共享预算、取消及未知用量还需原子预留 | 不是5次上限的解法，本轮不加并发 |

不采用：把首次工具选择算到“免费前置”、重开第二账本、隐藏恢复请求、删除completion、跳任一fresh、
把人工Host当产品免费服务。前置RAG可做，但必须作为新的检索设计评估，不能伪造已有模型工具消息。

## 6次候选的具体实施边界（尚未实施）

1. 记录用户决定并建立独立合同/指纹/Workflow，不修改既有冻结854源码、旧包或封存结果。
   如确需改共享实现，保留旧版本可回放，不能让旧身份静默承担新语义；不直接覆盖历史冻结文件。
2. 单个run、单个预算器计入每次模型发送，含工具选择、后续成稿及四审查。
   在双初审需要修订时、实际应用前检查至少还有两个调用slot；不足即停止，不先购买一个注定不完整的fresh。
   token按实际已用+未知预留+下一请求上界验收，所有时间归同一900秒墙钟；这不保证后续模型一定够用。
3. 程序只做严格block_N/唯一锚点/无重叠及原样应用。语义冲突、错补丁、正确内容损害不能靠这些检查认证。
   开发Host逐意见、兼容和四项ReportAssessment需映射到明确产品发布规则，并用完整反例验证。
   两个fresh都读同一实际新稿和完整来源，不能带旧结论；但fresh通过本身仍非独立质量认证。
4. 先以替身验证实际组装、普通修订、双方pass、额外工具轮次、预算不足、取消、坏补丁、fresh失败与未知用量。
   再按同版本/实际参数准备原15及自然消费验证；新付费计划另列具体成本和授权，不拿旧固定报告封存拼资格。

调用上限不是唯一阻断：当前产品单次300秒与开发time600身份不同；固定报告4次活动318.515秒
不含自然生成且排除了Host3959.876秒，不能推出产品900秒达标。6×(64000+32768)=580608高于
401920；这不是必须同步扩tokens的理由，现有预算器本就按实际用量和下一次预留动态准入。
不能以单例实际65839tokens替代新输入的容量与时间核验。
