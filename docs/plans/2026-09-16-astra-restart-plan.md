## 下一项交付：先把完整合同证明可执行

交付物是一份可审查的方案裁决及对应离线反例结果，随后才实现选中的替代合同。
先检查已有脚本与测试能覆盖什么，复用它们；不为本计划的每句话新造一个测试。

| 要回答的问题 | 工作与验收依据 |
|---|---|
| 审查对象如何稳定且不漏原文 | 比较程序预索引源单位与同预算完整重评；验证标题、表格、段落和跨段限定的覆盖、回跳与稳定身份。分段不等于语义正确。 |
| 首评错了是否真能修 | 按允许错误族检查重复、漏项、误分类、错误来源、范围漂移、说明错绑和超容量；每类要么有合法修复路径，要么在付费调用前明确拒绝。 |
| 纠正是否会删掉真实问题 | 在状态变换中保留原始回执、事实/安全问题及来源关联；不能靠删问题、改标签、缩小审查范围得到通过。 |
| 语义是否真的有依据 | 单独检查样本、分路、胜负组、指标和解释对象；合法样本观察与真实外推分别判断。程序检查无法证明的语义部分留到真实结果逐项人工核对。 |
| 整条链能否装进预算 | 测量完整首评、纠正、修订、复评请求和实际允许形状，沿用现有预约/实际结算合同；不能只测一个小片段，也不把五次最大值之和误当新增门槛。 |

选择依据是完整性、可纠正性、实现复杂度和实测请求尺寸，而不是哪种补丁最少。
若两种方案都不能满足当前合同，应交付具体冲突与取舍，不继续改提示词碰运气。
改变用户标准、预算、产品能力或正式采用的架构时，按对应决策边界处理；普通实现
选择和离线修复继续自主完成。

## 从离线设计到实际闭环

1. **离线合同裁决。** 完成上述整体比较、反例和容量核对，记录选定方案及局限。
   不直接解除旧候选的 `offline_only`，不增加 force/绕过开关。
2. **实现一个替代候选。** 共享输入、目标身份、纠正规则和最终验证；保留原报告
   成功基线及历史失败。运行与变更相称的回归和仓库规定检查。
3. **一次有解释力的真实验证。** 只有新候选满足离线合同及同实现公共检查后，
   才沿用既有授权和冻结正反例验证完整初评→必要修订→复评。人工核对判断、
   解释对象、来源和实际改文；一例失败即停批归因，不自动“补一处→再付费”。
   两例开发成功仍不等于代表性评估或生产准入。
4. **消费可信结果。** 合格后复用现有发布事务、Evidence 快照、观摩笔记及恢复
   接缝，验证 Coach/Training/Workbench 消费同一对象和结果；不另造发布管线。

最多 5 次调用、1 次修订、401920 tokens、900 秒，SDK retry=0。执行前从
`scripts/run_golden_integrated_review.py` 及所选新候选合同重新核对。
