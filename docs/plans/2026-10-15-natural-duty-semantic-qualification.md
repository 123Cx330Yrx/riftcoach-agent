# 自然互补职责：语义反例与同版本资格门槛

2026-10-15。零付费、离线设计，不改变 `1.6.0` 候选合同、默认入口或发布门。

## 已确认的结构反例

逐字补丁可以通过来源引用合法性、锚点、重叠和报告组装检查，却仍然没有语义通过证据。当前离线见证覆盖：

- 数字错误、范围扩大和无依据因果；
- `source_ids=[]`，仅靠结构校验无法确认解释和修法的来源支持；
- 补丁落在与 issue 无关的合法报告段落；
- 在逐字补丁中删除全部 `[K#]` 引用后仍形成结构合法的新稿；
- 两个职责给出不一致意见时，调用方传入 `conflict_status='clear'`。该字段不是认证过的冲突判断。

空来源并非一律非法：任务缺项可依据实际用户要求说明，不一定引用比赛统计。
无知识引用也要按适用性判断，不能把不适用的知识强加给任务。跨段修改可修直接影响的摘要；
本次错目标反例则只修改无关第6段，已知第4段错误仍保留。因此不为这些字段增加一刀切语义门。

直接补丁预览保存原样意见与改文；自然应用集成还核验六次共享调用、实际应用后的同稿双fresh、
Trace/receipt和Harness拒发布。替身即使把上述反例全部判为pass，最终仍是
`candidate_repaired_pass_unqualified`，`report_available=false`、Host语义未核验。
这证明未认证结果不流入发布，并不证明程序识别了这些错误。

## 六项开发Host工作如何对应产品路径

| 开发审查义务 | 当前候选中的实际承担者 | 尚缺证据 |
|---|---|---|
| facts完整意见及全部修法正确 | facts初审策略要求自己意见正确；程序保存意见/补丁 | 模型实际解释、来源和修法的质量 |
| completion完整意见不补造任务 | completion初审完整读取用户要求；自己的说明仍须事实正确 | 实际漏项、误报和越权修法的质量 |
| 两意见兼容 | 程序只拒重叠；自然候选没有caller clear门或独立兼容服务 | 不重叠的语义冲突不会被锚点证明为无冲突 |
| 实际新稿四项ReportAssessment | 唯一原样应用保留未替换字节；双fresh读取实际完整新稿 | 修改片段的事实、正确内容保留、身份和修复是否充分 |
| facts-fresh | 现有完整事实职责请求 | 双fresh可能共同漏判或误报 |
| completion-fresh | 现有完整任务职责请求 | 不能凭模型pass推定知识消费与实际任务已满足 |

因此暂不增加第7次模型或把开发Host作为免费运行时步骤；也不通过关键词、非空来源、
数值正则或caller flag伪造通用语义检测。当前组合可做研究候选；产品自动语义门仍待选择和验证。
旧有公开回执与本次替身反例只支持这个限制，不能证明某个新自动策略已经有效。

## 同版本资格的必要门槛

完整15的既有要求保留。当前1.6.0请求清单只绑定这份研究候选；若之后改变策略、合同或发布门，
必须重新绑定最终组合，不能把研究清单或旧成功迁移为新身份的资格。未来同版本验证应具备：

1. 保留15个原输入、原标签和所有历史分歧。标签仅在评估端使用，不注入模型请求；不得拼旧意见、旧封存成功或缺认证项。
2. 同一份完整输入、来源、原稿和用户请求进行双初审。正确稿双pass时直接结束，不要求编辑或fresh，也不记编辑消费证据。
3. 需修订时，核完整意见、全部补丁、来源支持、语义兼容和实际新稿四项质量；唯一应用后，对同一实际新稿完成两个fresh。非重叠和issue_ids齐全不替代语义评估。
4. 独立开发评估核完整来源与实际意见/新稿；这是评测证据，不能冒充产品运行时服务。拒绝或分歧不能认证；身份、协议、预算、来源、观测、回执或传输故障应按具体执行方案停止，不重试或补签。
5. 未发请求保留实际原因。双初审通过后按设计跳过编辑/fresh合法，故障后的未发不补齐成已完成。unknown、receiptless和发送未知分别记录，不能填0。
6. 同一自然任务仍共享6次/401920tokens/900秒、实际单请求300秒；工具轮次、生成和全部审查均占账本。固定报告测试不证明自然生成、900秒完成或产品消费质量。
