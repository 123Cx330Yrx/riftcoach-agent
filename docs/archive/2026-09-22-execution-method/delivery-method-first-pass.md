# 8E 推进方式纠正与执行裁决

日期：2026-09-22。用户要求先实质性纠正推进方法，再继续。

目标：恢复以真实 Agent 任务及其质量为单位推进，停止以评审候选版本和测试数量代替业务进展。
本文件取代旧计划中“下一步直接执行普通 native 单例”的排程，不撤销历史证据、既有业务验收或阶段顺序。
技术基础保持 Python / 现有 AgentRuntime、Tool Runtime、RAG、Memory、Worker / PostgreSQL / Workbench。

## 1. 当前交付对象与完成边界

当前 8E 观摩任务：用户选择公开 ShowMaker 观摩对象和复盘重点，系统绑定正确身份与数据，
由现有 Agent 调用知识工具、形成有来源的分析，审查并在需要时修订，通过后存储和展示同一结果。
错误或证据不足时保留可解释的失败状态，不发布错误报告。公开观摩不能成为用户本人的能力或训练基线。

这只是全项目的一条代表性任务，不是缩小产品目标。Coach 自然请求、Review、Training、Evidence
联动，训练的采用/反馈/版本、长期记忆和前端整体设计仍按原路线验收；固定复盘入口通过不能替代它们。
阶段退出条件仍以 roadmap、采用 ADR、能力矩阵及学习覆盖为准，不在这里新造阶段或质量阈值。

| 验收对象 | 当前可核实证据 | 尚缺什么 |
|---|---|---|
| 用户请求、身份与任务编译 | `app/product/recent_review.py` 的 typed request、observed 身份与 focus 编译 | 当前 runner 不是自由对话入口；自然语言路由到该任务及 Training 的完整体验不能据此算完成 |
| Agent 工具与上下文 | `app/product/native_coach_composition.py` 复用 AgentRuntime、RAG、可注入 Memory | 当前预览及脚本响应不证明真实模型的工具选择质量；观摩空 Memory 不证明个性化训练 |
| 分析、审查与修订 | `golden_native_issues_review.py` 及历史真实结果；最近单例改稿成功 | 正文误报和输出合同失败未解决；不同版本的局部通过不可拼成当前版本资格 |
| 同源结果与发布 | `FileEvidencePublicationStore`、native application 和 Worker 离线接线；ADR-0099 历史事务实现 | 当前合格模型结果的真实 Worker / PostgreSQL / API 消费证据，及实际默认组合的集成 |
| 用户可见完整体验 | 已有观摩笔记与 Workbench 实现；旧前端工作保留在主工作树 | 同一运行在 Coach / Review / Evidence 的展示、失败反馈；后续专属 Training 与整体前端升级 |

## 3. 纠正后的工作循环

1. 每批围绕一个业务阻断及真实调用路径。写明观察、竞争解释、最小改动、预期证据和结果如何改变技术决定。
   不把错误现象叫根因；先排查请求构造、来源和验证器自身，再把失败归因于模型。
2. 复用一个当前产品组合及其现有 runner。历史版本保留回放，不再把失败自动变成新 runner、Schema、恢复层。
   确需新协议时先列出旧协议无法承载的业务要求、被替换的复杂性和可修复路径；不因缺字段就增加语义任务。
3. 质量按完整上下文及来源判定。事实错误、真实外推、身份混淆阻断；可选措辞优化不升级成门槛。
   计算已有明确分组用确定性代码；自由文本究竟指哪个组仍需证明，不宣称已实现程序化语义裁决。
4. 工程验证与模型验证分开记结论。结构能过但意思错，记录语义失败；字段缺失不推出“模型不懂业务”。
   一批必要回归通过后继续交付，不因没有代码变化重复全库测试、CI 或旧成功探针。
5. 付费诊断必须有决策价值。沿用已授权 GLM/high 和现有预算，不从 Luna 开发协作推导产品参数。
   失败后保留原证据、停该批并归因；只有新的可区分假设或已证实缺陷修复才开新批，不无限微调措辞重试。
6. 每批记录业务能力变化、剩余阻断、实际已知/未知成本和下一动作；测试数、提交数、候选号不是完成指标。
   同步检查下游依赖，能独立完成的接线/设计工作继续推进，不能借失败绕过发布门或冒充正式交付。

这些是执行方式，不新增每步用户审批、固定实验轮数或“零误差概率”承诺。授权沿用；
改变业务范围、采用标准、模型/成本边界或正式架构时按现有约束处理。

## 4. 已作出的下一步裁决

不执行旧排程中的孤立普通审查单例：即使 pass，它仍不能决定产品是否可用，且已知普通 native
在相近完整上下文中有成功和失败。保留已冻结请求作为复用材料，不修改旧结果。
不恢复已撤回的 two-state 终评，不再单独修它的字段后付费重试。

改用当前产品原生审查链的一套统一资格检查，优先复用现有完整来源/报告，不新增评审层：

| 复用案例族 | 现有证据入口 | 要区分的业务行为 |
|---|---|---|
| 正确完整报告 | 6c22e93 实际正确改稿；scope_later_explicit / scope_intro_explicit | 理解跨段限定，不给作者添全称量词，不因建议性措辞阻断 |
| 同来源明确错误 | explicit_combined_population / explicit_universal_metrics；原归因和早死数值案例 | 找到真实分母/范围/归因错误，实际改对，再复审 |
| 真错与正确段并存 | 354d752 的实际混合报告与完整来源 | 修真错且保留正确内容，不把错误评估当事实 |
| 既有身份与来源回归 | observed_01 至 observed_05 | 观摩/本人、未来外推、官方日期、标题能力断言仍正确处理 |

以上是已有开发材料，不是新的独立 holdout。预期裁决留在测试端，模型不接收答案或人工改稿目标。
同版本完整资格沿用既有要求；不能只挑通过的几例。独立评估仍属于后续正式退出证据。

执行顺序与受影响文件：

1. **先修资格与产品绑定。** 复用 `scripts/run_golden_native_review.py`、现有结果/合同指纹和
   `scripts/run_native_coach_product.py`，移除“某历史文件五例通过即可”的未来准入隐患；
   正确拒绝旧版本、缺案例和失败证据。补充 `tests/test_native_coach_application.py` 中
   对应拒绝行为。保持所有 live 开关关闭；不为此创建第二套资格框架。
2. **审查当前原生任务负荷并做最小修复。** 在 `golden_native_issues_review.py` / 
   `golden_semantic_review.py` 实际输入、字段与验证规则中核对已有已证实合同缺口。
   不把 two-state 的恢复歧义移植回来；没有可证明改进时不靠新提示号直接重跑已失败案例。
   复用既有请求和反例验证修改后真错、误报、恢复路径及产品共享预算。
3. **有界真实资格，再真实产品消费。** 前两项及对应检查通过才按既有授权开始同版本批次。
   正确稿仍被误判，说明该候选不足以批准产品，回到输入/任务拆分的方案裁决，不能加规则原样续跑；
   真错漏检则针对证据使用定位，不能通过降低标准结清；协议失败先修具体合同，语义结论保留未知。
   全部相关质量证据齐全才开放产品实测，跑真实生成、工具、审查/修订和来源发布，而非只重放人工稿。
4. **复用发布设施完成消费。** 在已有 `native_coach_composition.py`、`workers/composition.py`、
   `tasks/recent_review_executor.py` 及事务/API 接缝集成；验证同一身份、运行和结果的持久化/恢复/展示。
   不重写 ADR-0099 的事务管线。真实 DB 和 UI 验证分别留证，不用上述 fake tests 替代。

仅第 1 项是下一项实施工作，不为步骤 2 预先决定新架构。若发现现有证据绑定能力已足够，直接复用。
完成每项无需再等“继续”；遇到需要改变用户业务决定的冲突才提问。
