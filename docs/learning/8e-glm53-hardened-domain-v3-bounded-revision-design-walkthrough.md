# 8E 学习记录：GLM-5.3 Flash V3 有界修订设计（RQ-231）

## 1. 问题与原则

RQ-230 的真实结果不是“模型没有响应”：Agent 完成了工具回合，拿到两个来源，注入检查也通过。
失败在于首稿被独立评测判定存在事实问题，分数 80 低于 85；而候选执行器把修订次数设为 0，
所以 Harness 没有机会运行产品本来支持的一次修订。

这里的原则是测试产品实际控制流，而不是为模型降标准。V3 保留全部质量与安全门，只把零修订测试
升级成一次受控修订测试；修订后仍必须重新评测，失败就拒绝。

## 2. 设计选择

比较了三种方案：只增加诊断、一次修订并增加诊断、降低门槛或改思考档。选择第二种，因为它既能
验证真实产品机制，又不改变 85 分、事实、引用、来源和注入要求。旧 V2 结果保持有效，不被“重考”
覆盖；V3 另建全新考卷与身份。

## 3. 数据与控制流

```text
初稿 → 第 0 次严格评测
  ├─ 通过：发布
  ├─ 安全阻断/明确失败：拒绝
  └─ 需要修订：最多修订一次 → 第 1 次同合同评测 → 发布或拒绝
```

公开回执只保存每轮分数、结论、通过项数量、问题类别计数和严重度计数。具体引用、证据说明、解释、
修改建议、正文和 reasoning 都留在私有运行工件中，不进入候选公开证据。

## 4. 为什么调用预算要重算

V2 的 4 次/案只够典型的“Agent 两次 + 一次评测”，无法覆盖修订和复评。现有控制流的可达上界为：
AgentLoop 4 次、首次评测及格式修复 2 次、修订 1 次、复评及格式修复 2 次，总计 9 次/案、27 次/域。

Token 不能只把旧数字乘二，因为后续评测和修订的输入会包含先前报告与问题信息。正确做法是在离线
阶段枚举每类请求包络，为每次最多 4096 输出预留，再冻结可达的有限上限；证明不了就不允许联网。

## 5. 验证与运行手册

实施时先用 Fake Provider 验证一次修订后通过、仍拒绝、安全阻断不修订、格式修复和资源耗尽；再验证
诊断模型拒绝任何自由文本字段，V2 的零修订和旧 Schema 不变。只有 no-I/O 准入、比例回归、公共 CI
和新鲜 G53-3-L 都完成后，才可以申请一次新的 V3 真实观察授权。

## 6. 边界

RQ-231 只完成设计，provider calls=0。没有修改适配器、默认 Runtime、GLM-5.2 手动兼容/应急路径、
Portal、Account、Workbench、Auth、路由或 `production_media=0`。它不证明候选已经通过领域门，
也不完成黄金切片、安全/部署/合规、8E 或 8F。

## 7. 面试表达

> 一次候选评测失败后，我没有降低质量门或原题重考，而是发现测试入口禁用了产品本来支持的一次修订。
> 我设计了全新版本：保持所有硬门，允许最多一次“评测—修订—复评”，并只公开枚举计数诊断；同时从
> 控制流推导调用上界，再用离线请求包络证明 Token 预算，避免为了通过而放宽边界。
