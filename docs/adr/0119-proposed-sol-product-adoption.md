# ADR0119: Flash/Sol 产品执行与发布合同提案

2026-10-30；状态 **Proposed，尚未采用或激活**。

## 要解决的问题

原15已经完整完成，自然任务的实际新稿也完成了正式应用与同稿双fresh。
普通 Worker 的持久续接已接好。现在缺的是把这些能力映射到明确的产品合同，
而不是继续用开发诊断的预算和 always-reject 出版结果代表产品。

当前旧角色合同是5次/401920 tokens/900秒；ADR0118已批准的独立候选是6次，
其余总量不变。当前Sol开发合同实际是10次/739840 tokens/3600活动秒，最多4次人工恢复。
这些身份不可互换。具体字段来自[本轮离线审计](../../data/evaluation/results/sol_product_adoption_budget_20261030.json)。

## 推荐采用的独立产品合同

| 项目 | 推荐值与含义 |
|---|---|
| 角色 | Flash/high选工具并成稿；Sol/high独立facts、completion；程序应用逐字补丁，不增加自由改稿模型请求 |
| 实际模型请求总上限 | **8次**，正常最短4次直接通过/6次修订；额外2个位置共用于追加检索或明确恢复，不能各算一份 |
| 共享token总上限 | **401920**，保留原产品/六次候选总量；已知使用＋未知预留＋下一请求包络共同受限 |
| 整任务时间 | **900活动秒**，单次至多300秒且受剩余时间缩短；跨进程、恢复累计，用户等待不计活动时间 |
| 单次输入/输出 | 输入上限64000；Flash输出32768，Sol输出16384，沿用当前角色参数 |
| 恢复 | SDK自动重试0；超时/可恢复格式故障每次明确操作最多补测1次，全任务最多2次，仍占8次和总tokens/时间 |
| 应用/复审 | 一次正式application；两个fresh读同一实际新稿。预算不足不先购买必然不完整的fresh，也不清零另开账本 |
| 激活 | 新合同/指纹与显式产品profile；不改历史合同或封存结果，不自动切换legacy默认，不自动扩展已有任务预算 |

8来自“最短修订6＋两个共享弹性位置”，不是实测最优值。相比机械保持6次，它容纳额外检索或一次失败后的同项恢复；
相比照搬诊断10次，它减少预设重试空间。保留401920和900是保守成本/响应约束，不是成功保证。
可以选择更严格的6次版本，但不能声称它同时保证动态检索、普通修订和两次恢复。

需要特别明确的代价：

- 6次各取最大包络已达515072 tokens，大于401920；按实际输入预留，正常短输入仍可达，但不能承诺所有上限输入都完成。
- 两次Sol fresh最大包络共160768，因此应用前累计已知＋未知预留必须不超过241152；随后仍逐次检查时间/包络。
- 900秒从旧单进程墙钟变为持久任务累计活动秒是明确的时间语义变更。等待用户期间可超过15分钟，计算期间不能重置900秒。
- 10/29封存父链8请求、122034 known＋73756 unknown可落在调用/token建议上限内，但实际记录1383.717活动秒，**不能说它满足900秒**。
  这条链含开发Host与继承过程；目前没有证据把这些耗时扣成“产品必能在900秒完成”。时间不足保留checkpoint，只暂停当前任务。
- 追加检索应保留完整审查所需位置；不能为了凑数跳completion或任一fresh。预算可达性是下一实现检查，不把提案数字写入当前运行配置。

用户在本轮切回official指Codex开发环境；本提案没有把产品Sol通道默换成官方API，也没有重估渠道价。
费用展示继续区分账面估计、已知tokens和未知预留，不能把token硬限宣传成金额硬限。

## 发布规则：使用完整链条结果，不要求线上Codex验收

新产品adapter沿用现有Harness/来源与owner权限，不依赖每份报告的开发Host/native作者。
现有开发adapter保持always-reject；新规则应在独立合同中实现，不能把旧记录的false改成true。

1. 初稿路径：两职责必须审同一实际报告和完整来源，各自满足现有85分/pass门槛，且没有未处理的阻断问题；
   不另外提高分数。可选建议、正常舍入不强制改稿。
2. 修订路径：两份意见的真实问题取并集。一个职责漏检保留为质量记录，另一职责给出的可靠补丁仍可继续。
   程序校验来源、唯一锚点和精确替换；相同补丁可去重，冲突不能靠任意顺序覆盖。无法可靠协调时只暂停受影响步骤。
3. 最终检查：唯一application、原正确内容与身份/用途/来源约束、两个fresh同稿且各自pass/达到原分数门槛，
   才可把候选成功映射到新产品的发布判定；fresh提出真实错误则保留新稿等待处理，不重新生成全部前缀。
4. 内容与证据权限继续由原发布/查询层执行。来源不完整时原有degraded/rejected规则仍有效；累计用量可见不等于报告可见。
5. 这些规则是自动化质量控制，不是“模型不会漏检”的证明。结构合法不能证明修法正确，双fresh也可能共同漏检。
   不把既有人工验收永久伪装成生产能力；下面的具体反例决定发布映射是否可启用。

## 采用实现前后的最小验证差异

| 待核项 | 复用证据 | 新增工作与失败处置 |
|---|---|---|
| 业务请求不漂移 | 原15、自然正式尾段、当前禁网库存 | 新合同仅改身份/预算/发布投影时逐字段比较；不因commit变化重跑15。若改变模型输入，再按实际变化列样本 |
| 预算可达性 | 旧共享预算器、当前持久累计用量 | 替身走4/6/额外检索、两次明确恢复、token不足/时间耗尽/未发取消；检查8次上限和双fresh预留，不购买新请求来测计数 |
| 发布与真实错误 | 历史错误修法、身份用途误写、正确稿/可选措辞、自然联合修订 | 将已保存完整材料接入新adapter的否定/保持控制；确认坏修法或任一fresh拒绝不能发布，联合可靠修订可以继续。离线通过不称新增真实模型质量证据 |
| 持久消费与权限 | 30真库检查、58前端检查及本轮浏览器操作 | 新profile/最终发布产物接入原API与查询权限后做定向真库检查；不重跑无关测试 |
| 真实产品通路 | 原模型实测与分段消费者验证 | 最终仍需一次有明确输入、请求上限和停止分支的代表性产品通路检查；不预设全新15例，另列具体付费计划而非沿用过期授权 |

原15的完成结论保留；同版本资格/全产品默认采用仍须按实际差异落地。若离线检查暴露真实缺陷，
先修具体机制，不叠加新阈值或再开一批模型碰运气。本提案不授权公开部署、产品数据库迁移、新付费批或Stage8E完成。

## 范围与下一步

本轮已实现暂停交互，独立于采用决定。正式合同建议采用8/401920/900、最多2次明确恢复；
需要用户确认的差异是请求上限、持久时间语义和新产品发布规则，而非重复确认普通工程修改。
确认后先离线实现独立合同和上述反例，再准备最小真实消费检查；默认切换和公开发布不与本提案捆绑。

后续前端整体优化、README/Demo打造、个人Training反馈、Workbench四块联动、知识/Memory、身份运维、
两树整合和独立评估/教学继续在总路线中。完成这个模型接线包不会自动完成这些工作。
