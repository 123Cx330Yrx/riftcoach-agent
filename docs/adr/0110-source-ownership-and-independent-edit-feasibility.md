# ADR0110: 来源职责与独立编辑的可行性核查

2026-09-24。状态：**三条独立编辑/替换路线未采用，旧批均关闭。来源投影修复已通过实际应用；当前1.5.1普通纠错链取得一例成功，随后正确全文误报，停止本批扩测。未采用新产品控制流，原15与产品仍未准入。**
本记录不修改 ADR0109 模型分工、用户完整上下文标准、原15资格或默认产品。

## 问题与目标

真实 Agent 观摩任务的 Flash 原稿把外部快照日期写成知识检索日期；GLM 初评漏检。
补齐知识时间及单条引用的来源信息后，6c3a3db 仍完整返回95/pass，并给一条正确建议
选择了不相干的指标来源。输入、报告、编号、传输及预算已核对，模型内部原因仍未知。
目标是降低这类错误进入用户报告的机会，同时保留 Agent 分析、工具、训练行动和完整质量门。

## 实际职责与控制流

当前 `ReviewHarness` 初评通过即发布。实际生成两次、初评一次后，五调用上限中仍有两次
未使用；但首评出现恢复或生成多轮时余量会减少。现有 `revise` 仅接收真实 needs_revision，
第二次 evaluate 要求已经修订一次。不能伪造 issue 或改写原 pass 借道进入这两个步骤。

生成器当前直接写完整七节 Markdown，包括来源目录。KnowledgeEvidence 已持有来源、
版本、文档更新和逐次检索时间，不必让模型自由重写固定目录。正文对来源的实际使用、
日期归属、身份/位置、复合指标、归因及训练建议仍是语义任务。

## 离线实现和决定

`app/evaluation/source_bound_report.py` 实现了一个未注册的组装原型：

1. 模型在第7节末留一个明确 slot；程序只替换该 slot，不定位并删除任何“像来源段”的正文。
2. 目录逐条从 KnowledgeEvidence 导出，重复检索、未知时间保持原义；不借外部日期补齐。
3. 原稿和成稿分别记录文本、摘要、操作及错误。失败也留原稿，不把主机呈现叫作模型改稿。
4. 修订必须保留已呈现来源块；改写则拒绝，程序不覆盖纠正。验证发生在既有终评绑定之前，
   接受的改稿字节原样进入终评、Harness 最终报告，未修改 `_expected_recheck` 私有状态。
5. 目录编号不使用 `[K1]`，所有来源值转义；来源名自己含方括号/换行也不能伪装正文引用。
   原有70%长度门只针对正文另行检查，固定来源栏不能掩盖正文大幅删减。

结构验证曾过于严格地拒绝原15中合法的描述性标题和附加小标题，已调整为识别真实标题行、
七节顺序和唯一性，同时保留这些合法内容及标题断言；未重写冻结报告或降低其语义要求。
最初直接把单参数 Harness preparer 包到双参数 SkillAgent preparer 上造成离线失败；已分别
识别现有两种结果合同，并保留原 AgentRun，实际 Runtime 五调用测试通过。

该原型已在现有 Harness 和**测试注入的实际角色 Runtime**走过两次生成/工具、
needs_revision、一次改稿、终评与文件读回；全部模型返回为脚本替身。不是新的 pass 后核验流程，
也不是产品候选接线或真实模型证据。原15只验证全文保留、来源与请求容量，未增加一次资格通过。

**不采用它作为核心漏检的充分修复。** 完整错误稿后加正确目录，保留原日期真错并重放
真实95/pass响应，现有校验仍接受。该负对照已保存，不能靠模板语法拒绝把旧例重标成“检出”。
目录方案仅保留为可复用的离线边界，本次新能力检查不同时启用，避免混杂干预。

## 完整流程约束与历史方案辨析

直接叠加专审会使需编辑的路径达到2生成+来源专审+完整首评+编辑+终评=6，超出5次。
用来源专审替换完整首评虽可凑成5次，但业务错误可能首次到终评才被发现，已没有编辑机会。
减少生成调用只有在实际检索、KnowledgeEvidence、Agent上下文、审查和发布同源时才有意义；
不能仅把知识塞进prompt、伪造工具历史，或用预设查询取消Agent按实际问题追加检索的能力。
现阶段先核对这些可复用接缝与失败分支，再选职责方案，不准备第三个付费变体。

旧`golden_source_first_review.py`是隔离首评解释/评分后的**完整全稿重评**，仍输出复杂
ComparisonWire和两类audit，并不是独立来源专审加普通业务评审。e23c90d真实新增一次Flash
第二评，96/pass但14个comparison字段缺失及来源错配；当时还有部分送达资料无引用地址的
合同缺口。旧block10“只能四场”裁决已经撤回，不能重新计为模型语义失败。
`golden_typed_review.py`在同一次复杂全稿输出中做source_checks，相关回执Provider calls=0。
因此目前既无“独立来源专审→普通完整评审”成功证据，也无其原样失败证据。
参考golden_source_first_result_e23c90d.json、golden_typed_review_offline_v1.json和
docs/plans/2026-09-19-review-oracle-provenance.md；模型内部漏检成因仍未知。

## 取舍和采用前要求

### 2026-09-24：选择先验证来源核验与显式编辑合并步骤

选择下一能力原型为：保留动态生成/工具、GLM完整首评，使用剩余的一次Flash编辑调用
独立核对来源事实并处理首评中的真实问题，只提交原文替换操作或空操作，最后由GLM完整
审查实际成稿。正常路径2+1+1+1=5；不增加第六次、不开第二个预算。不是已经采用的产品路由。

| 替代方案 | 本次决定 |
|---|---|
| 预设检索、强制一次生成以腾调用 | 不采用：ADR0011要求模型按需选择工具；目前KnowledgeEvidence仅从实际AgentRun工具结果汇集，预填prompt不是等价替换 |
| 独立来源专审后保留全部原步骤 | 不采用：需要编辑时6调用；放宽预算不是本包修法 |
| 来源专审替代完整首评 | 不采用：业务问题首次到终评才出现会失去修订机会 |
| 在编辑机会内核来源并提交显式修改 | 选择最小能力验证：保留完整首评/终评，未更改处可确定性逐字保留；是否补漏及是否按时完成仍须实测 |

具体变化是任务职责与编辑交付方式：原独立编辑要重新输出整篇报告，本原型只产出带block、
before、after、source_ids和reason的修改。程序验证原句身份、非重叠和引用存在后原子应用；
不自己删日期、不自动修正模型输出，不将操作合法称为事实正确。空操作原样保留错误稿也
必须能表达，作为“表示正确仍漏检”的负对照。标签和人工正确稿不进入模型请求。
这一变化不证明原300秒超时是由重写全文造成；即使输出短，推理仍可能耗尽时限或漏检。

保持、修改、拒绝三个分支必须明确：首评fail/安全问题终止；首评pass也须经过这一步和
完整终评；keep不伪造needs_revision，也不能绕过终评。编辑改变后的全文与原来源一起绑定
终评和发布，源变化/未知引用/重叠修改/输出失败拒绝。若生成多轮或评审恢复导致余量不足，
拒绝任务而不是跳过终评。当前Harness首评pass即发布的状态机尚未修改；本原型没有产品入口。

先用原日期失败、新正确参考和原15做身份/表达/容量检查，保留重复原句、跨段/多处修改、
删除段落、未知引用、无改动及错误keep反例。通过才准备有界真实能力检查；如果又漏检、改坏
或未完成，不推进产品控制流，也不追加提示变体重试。能力通过以后才实现明确的pass后核验
状态及真实编辑→终评；普通终评、完整15例和真实消费仍不可被两个能力例替代。

| 备选 | 决定与理由 |
|---|---|
| 再补字段/一句提醒重跑 | 不安排，已排除关键时间缺失，未获新的区分信息 |
| 静默删错误来源段或覆写编辑结果 | 拒绝，会隐藏模型错误并污染回执 |
| 固定来源目录 | 工程边界可用；不消除正文漏检和错引，不单独晋级 |
| 给所有任务追加第六次审查 | 不采用，超出既有调用预算且不能保证错误独立 |
| 使用预留编辑机会独立核验 | 本次300秒无正文，暂不采用、不加时重试；保留原失败 |
| 同错误请求直接换Flash审查 | 完整返回仍漏两处真错，不采用；正确参考未发，不拼旧归因例成功 |

未来若采用 pass 后核验，必须在正式 ADR 更新中明确原状态迁移、阶段身份、真实保持/编辑结果、
预算不足时拒绝而非跳过终评，以及普通 GLM 对实际成稿的完整审查。不能将两个实验的成功拼成整链。
默认模型、原始失败、旧15输入及主工作树前端未变；Worker/DB/API/Workbench消费、四块联动/
个性化训练、前端审美/必要重做/英雄头像、Memory/RAG、身份运维、两树整合和学习仍在原路线中。

## 显式编辑原型的冻结边界

`source_patch_editor.py`仅为未注册能力原型。全部操作先验证再原子应用，定位针对原稿，
未触及文字逐字保留；空操作不生成语义通过。独立复核发现并已修复真实标题/章节顺序
校验漏洞和“成稿未超长但完整终评请求超限”的漏洞；新增反例覆盖正文伪标题、围栏、
交换章节、重复标题、过大终评及不一致输入。人工裁决明确覆盖所有操作、所选来源、
